# 宿主控制扩展：未通过验收

状态：2026-10-18，北京时间。已发布版本保持 0.5.0、33 个工具。本分支的插件、公开参数、EQ 和发送扩展仍在开发，不能作为可用发布包安装；不要从本分支运行驱动安装器覆盖稳定驱动。

## 本机接口及实现范围

实际本机 Cubase LE 14.0.40 的随附声明有标准 EQ、发送和插件参数绑定，以及 DirectAccess 参数访问；没有新版 `mPluginManager/trySetSlotPlugin`。实现不激活 DirectAccess、不遍历原生对象树，也不读取声库或许可证材料。

| 模块 | 范围与限制 |
|---|---|
| `interfaces.py` | 区分实际本机声明、连接状态及运行观察 |
| `plugin_catalog.py` | 只读既有扫描缓存，内容 ID 和 revision；重复显示名拒绝。缓存存在不证明授权或可发声 |
| 驱动和 `host_controls.py` | 四段 EQ；本机四发送槽，上限八；乐器及前四插入槽的前六十四公开参数，溢出报告。返回宿主文本与归一化值 |
| 参数保护 | 停止走带、自动化写关闭、当前会话/UID/revision；Program 类参数只读，无目的地发送只读。已知版本的 Bypass 别名显式关联 |
| `plugin_ui.py` | 英文 Cubase 14 原生 Edit/WM_CHAR、精确叶项 OCR 及受限相对消息；需显式允许后备，未知初始化问题留给用户 |
| `plugin_loading.py` | 首个空插入槽或该插件首个同名乐器实例；Piapro 复用唯一实例。只清理确属本事务的新对象，恢复后完整回读 |

五个开发工具是 `cubase_get_interfaces`、`cubase_list_plugins`、`cubase_get_controls`、`cubase_set_controls`、`cubase_load_plugin`。测试进程显式设置 `CUBASE_PIAPRO_HOST_CONTROLS_PREVIEW=1` 才注册，默认仍为 33。生产 Codex 未开启此开关。

查询只序列化缓存，保留 `host-cache-1` 边界；MIDI 写请求只解析入队，mapping idle 派发标准绑定，不因超时重发。派发前冲突不恢复或覆盖其他修改；已派发请求及错误恢复均须完整宿主回读。插件身份为名称、厂商、版本和格式，未取得已加载 class UID，不宣称等价。

## 部分结果及新崩溃

仅在 E 盘独立空副本操作，原训练 CPR 未打开。EQ 第二段 \(3.0\,\mathrm{dB}\)、\(1000\,\mathrm{Hz}\)；RoomWorks SE 加载、参数、已知 Bypass 联动及注错移除；已连 Stereo Out 的发送电平、开关、pre/post 和注错恢复；Mutant 首个实例加载、参数和真实添加后注错清理，分别取得宿主回读，并比较其他组保持。尚未进行 Cubase 混音音频验收，也未验证任意插件。

同名 Mutant 第二次添加曾生成不含插件的空轨，原因未证实，已清理自己的新轨并限制重复添加。回调属性读取、激活时序、跨进程 Edit 文本等独立缺陷已有回归；这些修正不代表下述崩溃已解决。

23:09:51，关闭自己的工程并退出实例时出现新转储，整体验收失败。`0xc0000005` 位于 `Cubase14.exe+0x48f8405`，虚函数调用遇到无效对象；对象内存含 Piapro 配置交换文件路径片段，这不能判定 Piapro 是根因。该偏移与前次轨道查询的 `0x2cadca3` 不同，无厂商符号，具体来源未证实。

实际加载驱动、转储、源码、日志、截图和配置已备份，崩溃时驱动与后续未加载源码有区别。确认 Cubase 退出后，启动驱动已逐字节恢复稳定 0.5。原训练 CPR 和测试副本磁盘哈希未变。新功能未发布、安装或正式接入；转储及个人资料只留本机 E 盘。

## 崩溃后拒绝现场指令

`host_health.py` 在现场目标入口和每条 MIDI 发送前检查 OS 进程启动时间及 Cubase 报告目录。新报告只读取有界的头、目录和 MiscInfo，匹配 PID 与创建时间；其他实例及复用 PID 的旧报告不归因于当前进程。新报告尚未写全或格式不明时保守拒绝；进程或报告状态不可读也拒绝。文件工具不因此关闭。

报告匹配时返回 `HOST_CRASH_DETECTED`，状态不可核实时返回 `HOST_HEALTH_UNVERIFIED`。参数派发前被拒绝不重发、不尝试恢复写；派发后未知结果仍依赖实际回读，但恢复请求本身也经过发送检查。此保护依赖报告已出现，不能预防最初的原生异常，也不能消除检查与实际发送之间的竞态。

本机已有新转储的 MiscInfo 已确认原故障 PID 为 36308。另用 E 盘合成报告匹配真实测试 PID，实际公共状态入口返回拒绝、没有打开 MIDI 端口；恢复真实报告目录后宿主反馈正常。合成报告没有写入真实 Cubase 报告目录，没有触发或伪造一次实际崩溃。

进程时间和报告格式参考 [GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)、[MINIDUMP_MISC_INFO](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/ns-minidumpapiset-minidump_misc_info)。没有引入新运行依赖、私有原生访问或全局调试设置。

## 解锁后对照结果

2026-10-17 深夜至 10-18 下午，十三个独立空副本完成关闭、退出码零及转储核验。稳定驱动/故障时原件的空工程、两者修改原有音量、立即退出时序、RoomWorks 加载/移除、Mutant 单次及连续三次创建/移除、EQ 批量写、Piapro 旁路恢复、发送目的地与 pre/post、组合流程及重复 Mutant 失败路径均未复现原关闭崩溃。每轮结束恢复稳定启动驱动。

第二个 Mutant 仍复现“创建空轨但未加载插件”，正式工具提前拒绝同名重复添加，随后按自己的 UID 清理并回读。该失败后再次正常加载/移除和关闭也未产生新转储；不能据此认定空轨就是原始崩溃根因。

组合流程另隔离一个确定的 OCR 误拒绝：原生确认框只有按钮、没有消息文本或 owner 关联，中文 OCR 将固定短语识别为 `Discard 訓 changes t0`、名字间连接符识别为下划线。先失败的实际文本回归后，加入仅此语言的静态别名；完整单行问句、精确两端名字、Discard/Keep 按钮仍须成立，名称内部标点不替换，额外内容及歧义拒绝。正式代码已接受真实问题、完成移除、全部参数组回读及退出。没有勾选不再询问。

最后增加一次独立副本的跟踪关闭，合计十四组取得退出码零和转储核验。Microsoft 签名的 ProcDump 仅附加本次自有 PID，过滤首次访问违规；三次 Mutant 循环、EQ、RoomWorks 参数及旁路、Piapro 旁路、发送与插入恢复均有实际回读。窗口最小化曾触发布局拒绝，恢复核验成功；恢复该测试窗口后接续。最终 Cubase 和监视器退出码均为零，日志明确记录进程退出，没有捕获访问违规，也没有新转储。未注册全局调试器或启用堆校验，监视器不常驻。

另一次较早的跟踪缺少退出记录，随后关闭入口返回 `CUBASE_PROJECT_NOT_UNIQUE`；它不计入上述十四组，也不能作为正常退出证据。它没有新转储，下一次启动显示了无故障文件信息的 unexpected termination 提示，具体结束原因未知。不能用后来的成功覆盖此证据缺口。

最终完整离线回归 203 项通过、无跳过，耗时 \(721.69\,\mathrm{s}\)。已恢复稳定启动驱动和 ProcDump 的 EULA 单值原状态，确认无自有 Cubase 或监视进程残留；原训练 CPR、模板和测试副本磁盘哈希保持。所有上述未复现结果和保护修正都不构成原生根因修复，新扩展继续未发布、默认关闭。

## 完整捕获与关闭流程修正

### 10-18 完整内存捕获

在新的 E 盘独立恢复点，使用本机微软签名的 CDB，从启动捕获首次访问违规、堆损坏和 fast fail。只使用自有空副本，不安装全局调试器。先以独立探针核验实际文件的 FullMemory、Memory64 和 Exception 流；探针不计作 Cubase 证据。四份 Windows 符号按原转储 GUID/age 从微软公开服务器直存 E 盘各自独立目录。原小转储已展开主线程至入口的 38 帧，Cubase 内部仍为模块偏移，未取得厂商私有符号。

| 对照 | 实际结果 |
|---|---|
| 故障驱动，普通堆，重复乐器失败与后续参数/插入/发送同进程 | 完整回读、目标与调试器退出码零，无异常 |
| 故障驱动，默认调试堆 | 清理反馈超时后关闭，实际捕获 `c0000005`，完整文件约 \(2\,\mathrm{GiB}\) |
| 故障驱动，默认调试堆，零 MIDI，仅开关空 Piapro 副本 | 同偏移 `0x485ab70` 的实际 AV，完整内存已保全 |
| 稳定 0.5 驱动，其余同上 | 同偏移 AV；新增参数/EQ/发送绑定不是该复现的必要条件 |
| 稳定驱动，零 MIDI，改成一次原生 File/Quit | 最终退出，无 AV；中间线程在 CRT 退出堆释放中持续工作。未保存最终目标退出码，不补造零值 |
| 稳定驱动，零 MIDI，原两段关闭，抑制所有 popup 初始化 | 审计确认抑制 66 次、实际分发零次，仍捕获同偏移 AV；排除其为该故障必要条件 |

| 空诊断驱动，无宿主访问/绑定/回调，零 MIDI，原两段关闭 | 运行时内存已核验脚本身份；仍捕获同偏移 AV、同类 free fill 块。上述 MCP 代码不是必要条件，尚未完全移除 MIDI Remote 子系统 |
| 稳定驱动，普通堆，修正为仅一次原生 File/Quit | 目标、客户端和调试器退出码均零，无 AV、无新原生报告 |

默认调试堆的 `NtGlobalFlag` 实读 `0x70`。完整堆明确显示一个相关块处于 `free fill`，正在使用的另一块为 `busy extra fill`，证实这次复现涉及已释放对象。随后标准硬件观察点补齐了存活时类型与第一次释放的栈。新故障偏移与原始 `0x48f8405` 不同；共享后段调用链尚不足以逐对象证明原报告。已经排除查询请求、Mutant 操作和 MCP 宿主访问/绑定/回调作为本次复现的必要条件；这不等价于完全移除了整个 MIDI Remote 子系统。

菜单枚举的 popup 消息配对和位置问题已依据 Windows 契约确认，但上述对照不支持将其当作这次崩溃的修复。没有叠加猜测性生产补丁。全部转储、符号和临时诊断脚本仅留本机，不放入源码仓库。

随后硬件写监视补齐了释放来源：工程关闭时创建的 `UProgressDialog` 被嵌套消息循环处理的应用退出提前释放，随后外层工程清理继续使用它。保存了健康状态、仍存活的进度对象和实际 AV 的完整内存，以及首次释放的 `RtlFreeHeap` 调用栈。后续 `mediaclient` 等模块只复用了同一地址，不能把这些复用写入当作最初破坏者。临时诊断脚本有一次 MASM 条件语法错误，停在普通观察点后修正，不计为应用异常。

本次复现的机制已明确，自有验收脚本需要改成一次原生 File/Quit，并持续监视实际退出；不能在项目窗口刚消失时追加应用关闭请求。生产 MCP 当前没有公开的自动关闭工具，不能把该脚本修正宣称为已修复 Cubase 本体。原始小转储只有部分内存，仍不能逐对象证明原始偏移与本次完全相同；原故障发布门槛保持。

实际只修正了本机副本验收脚本，并完成上表普通堆/默认调试堆的回归。两组的原生报告清单保持、真实句柄退出码零；稳定驱动、自己的 MIDI Remote 映射文件已恢复，原训练 CPR 哈希保持，现场无遗留 Cubase/CDB，loopMIDI 保留。全局调试注册表和原先不存在的 ProcDump EULA 键均未改变。

## Codex 运行包隔离

核查发现旧配置调用 `run_server.py`，会优先加载开发 `src`。已安装 0.5.0 wheel 和只注册 33 工具不能证明后端代码与稳定包一致。安装器现默认用隔离 Python 启动已安装模块，忽略工作目录和 `PYTHONPATH`；缺包时在修改配置之前拒绝。真实子进程的冲突源码回归先失败后通过，安装器专项六项通过；运行包和原已验收 wheel 的 47 个文件逐字相同。

本机仅更新该服务器的启动参数，实际配置备份保留 E 盘，其他 TOML 值不变。CLI 读回及从保存配置启动的全新 SDK 连接已验证：0.5.0、33 工具、文件读取 SHA 一致、无现场 MIDI 请求，新五工具不存在。旧进程已导入的源码仍需重新连接才会替换；没有强制重启整个 Codex 或中断其他聊天。此修正只固定稳定包入口，没有构建、安装或发布新扩展。

## 尚未通过的门槛

原始无效对象访问与新进度对话框故障的精确关联仍需证据，不能事后恢复原小转储缺失的内存，也不能通过当前代码修改厂商内部实现。后续只在自有副本、单次退出协议下继续，保留首次异常的完整内存和调用时序；结束即退出诊断工具，不常驻等待、不上传转储、不操作原工程。

根因修正、针对性回归、SDK 实际新工具调用、组保持/恢复、现场恢复及正常退出通过后，才能构建、安装和正式接入。离线通过、发送成功、进程退出或单次不再出现均不足以宣称根因修复。接续状态见 [项目记忆](project-memory.md)。
